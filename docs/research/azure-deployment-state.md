# Azure Deployment State — Comprehensive Assessment

**Date:** 2026-02-26
**Context:** PostgreSQL Flexible Server quota approved by Microsoft. This document captures the full state of Azure deployment readiness across all code layers.

---

## Executive Summary

The Azure deployment is **feature-complete at the infrastructure and application layer**. All Terraform resources are defined, CI/CD pipelines are operational via GitHub Actions, and the Go API + synth-service have full Azure Blob Storage and Azure AD Easy Auth support. The PostgreSQL quota approval unblocks the final infrastructure provisioning step.

**Key gaps identified:**
1. Three Python sidecars (phi-detection, classification-service, defacing) lack Azure AI/cognitive service backends (they have GCP + AWS equivalents)
2. CI validation (`ci.yml`) does not include `terraform/azure` in the Terraform validation matrix
3. No post-deploy health check in the GitHub Actions deploy workflow
4. DIMSE VM deploy script has a fragile `docker inspect` call on first run

## 3. Go API Azure Support

### Storage (`api/storage/azure.go` — 193 lines)

**Status: COMPLETE**

Implements full `Storage` interface:
- `NewAzureBlob()` — `DefaultAzureCredential` (managed identity in Container Apps, env vars locally)
- `GenerateUploadURL()` / `GenerateDownloadURL()` — SAS token generation with 10s clock-skew leeway
- `Store()` / `Retrieve()` / `List()` / `Delete()` / `Move()` / `Size()`
- `Move()` uses copy-then-delete (Azure has no native rename)
- `Delete()` is idempotent (handles BlobNotFound)

**Dependencies (go.mod):**
```
github.com/Azure/azure-sdk-for-go/sdk/azcore v1.16.0
github.com/Azure/azure-sdk-for-go/sdk/azidentity v1.8.0
github.com/Azure/azure-sdk-for-go/sdk/storage/azblob v1.5.0
github.com/AzureAD/microsoft-authentication-library-for-go v1.2.2
```

### Authentication (`api/middleware/auth.go`)

**Status: COMPLETE AND TESTED**

`azureUser()` function reads `X-MS-CLIENT-PRINCIPAL-NAME` header set by Azure AD Easy Auth. Falls back to API key bearer token. Integration test exists in `auth_integration_test.go`.

### Config (`api/config/config.go`)

Two Azure-specific fields:
- `AzureStorageAccount` from `AZURE_STORAGE_ACCOUNT`
- `AzureStorageContainer` from `AZURE_STORAGE_CONTAINER` (default: `dicom`)

### Initialization (`api/main.go`)

Storage mode switch at startup:
```go
case "azure":
    azStore, err := storage.NewAzureBlob(ctx, cfg.AzureStorageAccount, cfg.AzureStorageContainer)
```

### Database

Cloud-agnostic PostgreSQL via `pgx` driver. `DATABASE_URL` or `DB_*` env vars. No Azure-specific connection handling needed — standard PostgreSQL DSN works with Azure Database for PostgreSQL Flexible Server.

## 7. Identified Gaps and Issues

### Fixed (2026-02-26)

1. ~~**CI validation missing**~~ — **FIXED.** Added `azure` to `ci.yml` Terraform matrix with required `TF_VAR_azure_ad_tenant_id` and `TF_VAR_db_admin_password` CI placeholder vars.

2. ~~**DIMSE VM deploy fragility**~~ — **FIXED.** Reordered `docker inspect` before `docker rm -f` in deploy-azure.yml so env vars are captured from the running container before removal. The `|| echo ''` fallback handles the first-run case where no container exists.

3. ~~**No post-deploy health check**~~ — **FIXED.** Added `health-check` job after deploy phase. Retries `/healthz` up to 5 times with 15s delays, fails the workflow if API is unhealthy.

4. ~~**Azure AI backends missing**~~ — **FIXED.** Added `azure_vision` backends to phi-detection (Azure Computer Vision Read API for OCR) and classification-service (Azure Computer Vision image tagging). Includes `INCLUDE_AZURE_VISION` Dockerfile build args, docker-compose.yml entries, and full test suites.

### Remaining (not blocking deployment)

5. **No rollback automation** — If a deployment breaks the API, there's no automatic rollback. Must manually `az containerapp update` with a previous image tag.

6. **Application Gateway WAF disabled** — Using Container Apps built-in HTTPS ingress initially. No WAF protection until Application Gateway is enabled with a TLS certificate.

7. **No geo-redundancy** — Storage is LRS, PostgreSQL backups are local only. For production HA, consider GRS and geo-redundant backups.

8. **Azure deployment scripts** — Unlike GCP (`scripts/gcp_*.sh`) and AWS (`scripts/aws_*.sh`), there are no `scripts/azure_*.sh` helper scripts. All setup relies on Terraform + GitHub Actions.

## 8. DIMSE Receiver Enablement (All Three Clouds)

The DIMSE receiver (DICOM C-STORE SCP on TCP 11112) is opt-in on all three clouds — set `dimse_receiver_image` to a non-empty value in `terraform.tfvars` to provision the VM and networking.

All three clouds use `dimse_source_ranges` to restrict inbound DICOM traffic. The default placeholder (`203.0.113.0/24`, RFC 5737 TEST-NET-3) is non-routable — **replace with real PACS IP ranges before production use**.

### GCP (Compute Engine)

```hcl
# terraform/infra/terraform.tfvars
dimse_receiver_image = "us-central1-docker.pkg.dev/aegis-prod-488120/aegis-services/dimse-receiver:latest"
dimse_api_url        = "https://api.aegisimaging.ai"
dimse_project_slug   = "default"
dimse_source_ranges  = ["203.0.113.0/24"]  # replace with PACS IPs
```

CI/CD: Cloud Build updates the VM metadata and resets the instance on each push to `develop`.

### Azure (Linux VM)

```hcl
# terraform/azure/terraform.tfvars
dimse_receiver_image = "<acr-name>.azurecr.io/dimse-receiver:latest"
dimse_vm_size        = "Standard_B2s"
dimse_ssh_public_key = "ssh-rsa AAAAB3Nz..."
dimse_source_ranges  = ["203.0.113.0/24"]  # replace with PACS IPs
```

Also set the GitHub variable `AZURE_DIMSE_VM_NAME` to the VM name (e.g. `aegis-prod-dimse-receiver`) to enable CI/CD deploys via `az vm run-command invoke`.

### AWS (EC2)

```hcl
# terraform/aws/terraform.tfvars
dimse_receiver_image = "123456789012.dkr.ecr.us-east-1.amazonaws.com/aegis/dimse-receiver:latest"
dimse_source_ranges  = ["203.0.113.0/24"]  # replace with PACS IPs
```

CI/CD: GitHub Actions updates the SSM parameter `/aegis/dimse-image` and reboots the instance.

### Firewall / Security Group Details

| Cloud | Resource | Variable | Default |
|-------|----------|----------|---------|
| GCP | `google_compute_firewall.dimse_ingress` | `dimse_source_ranges` | `["0.0.0.0/0"]` |
| Azure | `azurerm_network_security_group.dimse` (NSG rule) | `dimse_source_ranges` | `["203.0.113.0/24"]` |
| AWS | `aws_security_group.dimse` (ingress rule) | `dimse_source_ranges` | `["203.0.113.0/24"]` |
